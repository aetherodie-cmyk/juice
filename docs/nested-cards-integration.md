# 巢狀卡片整合進正式白板：技術方案

這是接續 JUICE-UI-001 原型的**規劃**，不是已完成的正式白板功能。原型仍使用獨立 `nested-cards.html`、`juice-nested-prototype-v1` 與 `juice-nested-board` v1；不得把原型 JSON 直接交給正式白板匯入入口或覆蓋使用者白板。

## 建議的整合邊界

1. 正式白板保留現有 `cards`、`links`、`groups`、`images`、`icons`、`notes`、Classic 與 Flow Plus。巢狀容器／工作只作為新的可選白板內容，未使用它的白板保持原有操作與布局。
2. 把 `nested-core.js` 的驗證、引用路徑和避讓演算法抽成可供正式白板呼叫的模型；把 `nested-app.js` 的畫面改為可 mount 的元件，透過既有 `scheduleSave`、`touch`、undo／redo 與連線刷新路徑保存。正式版元件不得自行寫另一個 localStorage key 或直接寫 Drive。
3. 為正式白板訂立新的資料版本，例如 `schemaVersion: 4`，在根物件加入可選 `nested`：`objects`、`memberships`、`placements`、展開狀態。`purpose` 仍只適用容器，既有 v1 原型沒有此欄位時讀成一般容器。`cards` 繼續保存舊卡；工作只存一筆，引用保留穩定 ID，不複製資料。
4. 原型的 `boardPositions` 是預覽用覆層，不能在遷移時偷偷覆寫正式卡片座標。匯入原型時顯示原白板 ID、卡片數、巢狀物件與位置變更摘要，讓使用者選擇建立**新本機白板副本**；只有明確選擇後才把覆層套到副本。原型內的 `board` 與目前正式白板不一致時，不做靜默合併。
5. 載入新版白板時，舊前端必須因版本不符而拒絕儲存，避免舊版 `Core.normalize` 丟掉 `nested`。升級路徑需驗證 schema 1／2／3 到 4；每個新增欄位都要通過 normalize、重載、匯出／再匯入、複製、undo／redo 與 Drive mock 往返。

## 介面與發布順序

先在主白板提供「建立巢狀區域／從原型匯入副本」入口，保持自由編排與原有卡片入口。展開卡片只推開必要鄰卡；共用工作卡面保留用途、層級路徑與引用提示。將手機觸控、長路徑截斷、同一工作多處同時編輯、連線端點以及大量圖片白板列為正式版驗收。

第一個整合 PR 應只加入資料遷移、模型與隔離入口；第二個 PR 再接主白板互動與同步，避免一次改寫 `app.js`、資料格式和 Drive 協調。發布前匯出重要白板、驗證真實 Drive 衝突及 OAuth，取得該次正式發布授權；CI 通過和 Pages 成功都不等於使用者資料已安全遷移。

尚待產品決定：巢狀物件要與一般卡片共用同一畫布，還是作為可開啟的區域；展開狀態是否跨裝置同步；原型位置覆層是否導入正式副本；工作卡是否需要正式的刪除／解除引用與權限規則。這些決定之前，不把原型與正式白板資料自動混合。
